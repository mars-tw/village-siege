# R25 觸控策略玩家實玩報告（1.1.0 修改後）

## 測試條件

- 本機整合版：`http://127.0.0.1:5174/`，畫面版本 1.1.0
- 瀏覽器 session：`r25-touch-after`
- 主要尺寸：Chromium 行動裝置模擬 844×390，`maxTouchPoints=1`、coarse pointer
- 短尺寸：568×320、667×375；另測 375×667 直向與旋轉回橫向
- 對局：河谷鎮、攻城戰、標準難度、均衡 AI
- 正常遊戲時間：至少 8 分鐘；工匠與科技 dialog 的暫停時間、manual reload 時間未計入
- 這是 AI 以熟悉 RTS 的觸控玩家身分實玩，不代表真人調查。

## 結論

娛樂度由修改前的 **5/10 提升到 7/10**。最大的差別不是數值變多，而是我終於能執行原本想做的經濟配置：工匠 1 採糧、工匠 2 伐木、工匠 3 採石。這三次都是從公開可見 snapshot 建出的原生 dialog 下令，每次只改派一名工匠。之後我用兵營與木作營升到城寨期，再訓練戰士；發展路線從「全選全部工匠反覆改採同一種材料」變成可預期的糧、木、石並行。

科技面板也比修改前實用。缺木作營時可以直接點「+ 木作營」，完成前置後會顯示城寨期成本與「約 45 秒完成」。這讓等待有明確目的，也讓玩家知道下一步要做什麼。

## 工匠分工驗證

844×390 時，面板每頁顯示 2 名工匠；568×320 每頁 1 名；667×375 每頁 2 名。每列都有選取、採糧、伐木、採石，並顯示目前狀態與攜帶材料。翻頁與關閉始終可見。

所有按鈕高度至少 44 CSS px。568×320 的四個單工匠操作按鈕各約 125×44，667×375 約 102×44；關閉、上一頁、下一頁都在 viewport 內。dialog 開啟 5 秒前後兩張截圖 SHA-256 完全相同，關閉後 5 秒畫面開始變化，證明開啟時會暫停、關閉後恢復。

這個面板也修正了策略層的主要卡點。玩家不必先在十幾像素高的角色群裡精準點中某一名工匠，才能分派工作。施工中的工匠仍顯示施工狀態；只有按下某一列的資源按鈕，才會改派那一名工匠。

## Canvas 原生控制

844×390 的主要控制都在 viewport 內：底列按鈕約 61×64，科技按鈕 101×48，工匠分工 96×48。修改前 proxy 只有 16×6 且落在 `y=390`；修改後 Playwright 可以直接以原生 click 點擊，不再回報 `outside of the viewport`。

實玩前半段發現一個雙派送問題：原生 proxy click 先執行一次，Phaser pointer-up 又在已更新的 current actions 執行第二次，所以「建造」會直接跳到兵營放置，「返回建築表」又立刻選回兵營。主線修正後我手動 reload，再匯入自己的實玩存檔重測：全選工匠只執行一次；建造會停在建築表；返回只回一層；訓練戰士一次只讓佇列從 0/5 變成 1/5。這項問題已通過修正後驗證。

## 發展、戰鬥與娛樂度

三路採集讓我能先用一名工匠蓋兵營，再從科技面板補木作營，資源不會因為整批改派而完全停止其中一種。城寨期完成時有清楚的畫面訊息；兵營訓練成本與佇列也容易理解。

AI 在這場仍會接近基地，畫面曾提示「敵軍攻勢逼近」。攻城戰把「摧毀核心」寫進勝利條件，比修改前不知道往哪裡進攻清楚。不過我仍沒有在八分鐘內走到真正攻城，戰鬥回饋主要靠提示與血條；攻勢方向、小地圖與交戰摘要仍有改善空間。

系統→鏡頭視角裡可以關閉音效，按下後控制文字會切成「開啟音效」，觸控回饋清楚。

## 短螢幕與旋轉

- 568×320：工匠 dialog 不溢出，每頁一人；所有按鈕 44 px。
- 667×375：工匠 dialog 為 631×283，科技 dialog 為 631×363，兩者完整落在 viewport 內；科技面板所有按鈕 44 px。
- 375×667：遊戲顯示「請將手機橫向；旋轉完成後操作按鈕會恢復」，canvas native controls 為 `display:none`、0×0。
- 回到 667×375：狀態顯示「橫向操作已恢復」，底列 61 px、科技與工匠分工 48 px，全部恢復且在 viewport 內。

## 存檔／Continue 修正驗證

第一次匯入較舊的自己存檔時，遊戲顯示「無法自動存檔」。只讀比對證實：匯入檔是 tick 3692，但 IndexedDB latest 已到 tick 7376，同 matchId、同 seed；舊的 stale-write 防護拒絕了恢復後的時間線。

加入 explicit manual restore 後，我再 manual reload，從 UI 匯入同一份 tick 3692 存檔。畫面顯示「存檔已匯入」，IndexedDB latest 立即改為 3692，原本較新的 tick 10078 留在 previous。離開戰役後主選單能 Continue；Continue 後手動匯出 tick 4396，仍是同一 matchId／seed、城寨期、無已完成科技、建築佇列皆為 0，資源則從糧 575／木 25／石 840 正常發展到糧 718／木 25／石 970。最新 autosave 也繼續前進，previous 仍保留 10078。

## 最終 freeze 補驗

主線最後修正 667×375 的 Continue 遮擋後，我用新 session 從 UI 建立真實 autosave，再於 844×390、667×375、568×320 重測戰前頁面。三個尺寸各有 18 個可見按鈕，最低高度都是 44 px；每個按鈕中心的 `elementFromPoint` 都命中自己，全部落在 viewport 內。三個尺寸的 `window.scrollY`、`#game-root.scrollTop` 都是 0，頁面高度分別等於 viewport 高度。

667×375 的 Continue 原生 click 已成功進入戰場；Canvas 是 `x=0, y=0, 666×375`，`#game-root.scrollTop=0`、`scrollLeft=0`。因此先前 `.frontier-bottom` 攔截 Continue 的問題已關閉。工匠分工的單次指派與議事堂的單次訓練也再驗一次：一個原生 click 只出現一則成功狀態，生產佇列只從 0/5 變成 1/5。

仍可改善的體驗是攻城節奏與軍隊可讀性。攻城目標比修改前清楚，但八分鐘內仍沒有形成可見的「偵察到核心→組軍→推進→攻城」完整循環；小單位在建築與樹旁也容易重疊。
